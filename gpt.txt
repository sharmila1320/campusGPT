# 1 — Project Summary (elevator pitch)

**CampusGPT — The AI Brain for NIT Silchar**
A multi-modal conversational agent and campus assistant that answers student queries (schedules, professors, buses, events, library, clubs), provides personalized recommendations (events/committee invites), surfaces campus news, and routes unresolved issues to admins. It combines RAG (vector retrieval), a lightweight knowledge graph, an admin feedback loop that updates memory, and a modern web kiosk + chat UI that can be deployed on college pages, club sites, and a physical kiosk.

Key outcomes: deployable product, dashboard analytics, active user base (students), measurable improvements in query resolution, and a research/metrics section comparing retrieval strategies and active learning.

# 4 — High-level Architecture

1. **Ingestion Layer**

   * Scraper (Puppeteer/BeautifulSoup) for static pages & PDFs (pdfminer, PyMuPDF)
   * Manual uploader for admin to add PDFs, DOCs, announcements
   * Preprocessor: text cleaning, chunking, metadata extraction (title, source, date)

2. **Indexing**

   * Embed chunks → push to VectorDB (Pinecone/Milvus)
   * Save chunk metadata → Postgres (source, doc id, chunk id, keywords, embeddings pointer)
   * Build lightweight entity table (professors, courses, locations)

3. **Query Flow**

   * User sends query (Web UI)
   * Backend: check cache (Redis)
   * If cache miss: perform vector search → top-k chunks
   * Compose prompt: system prompt + retrieved context + user query
   * Call LLM (OpenAI/Anthropic) → answer
   * Post-process: classify “answer_confidence” and “source citations”

4. **Admin Loop**

   * If answer_confidence < threshold OR user flags “wrong”: route to admin
   * Admin answers via panel → saved as canonical reply → re-embed + update vector DB
   * Log correction for metrics & future fine-tuning

5. **Analytics**

   * Track metrics: query count, unique users, resolution rate, avg latency, top queries
   * Dashboard displays trending topics, unanswered questions, active users

Diagram (conceptual):
User → Frontend → Backend → (Cache → VectorDB → LLM) & Postgres → Frontend
Admin Panel → Backend → Postgres & VectorDB updates

# 7 — REST API Endpoints (sample)

* `POST /api/query` — {userId?, query} → returns {answer, sources, confidence, queryId}
* `GET /api/query/:id` — get query log
* `POST /api/admin/correct` — {queryId, correctedAnswer, tags} → stores correction & updates index
* `POST /api/upload` — multipart form: {file, title, metadata} → ingests doc
* `GET /api/analytics` — aggregated metrics
* `GET /api/top-queries` — trending queries
* `POST /api/auth/login` — basic auth or SSO
* `GET /api/docs/:id` — fetch doc metadata

# 8 — RAG / ML Pipeline Details

1. **Chunking**

   * Split doc into ~500-token chunks (overlap 50-100 tokens)
2. **Embeddings**

   * Use high-quality embedding model (OpenAI text-embedding-3-small or all-MiniLM)
3. **Index**

   * Upsert into Pinecone with metadata: {doc_id, title, url, section}
4. **Retrieval**

   * Use vector similarity + metadata filtering (e.g., doc_type=notice)
   * Top-k = 5–8 chunks
5. **Prompting**

   * System prompt: campus rules + response style (short, cite sources, ask clarifying Q if ambiguous)
   * Provide context chunks then question
   * Include “if cannot find answer, say ‘I don’t know — will notify admin’”
6. **Postprocessing**

   * Extract sources from returned answer (if model references chunk ids)
   * Compute confidence: heuristics (LLM self-reported, overlap score, length)
7. **Human-in-loop**

   * If confidence < 0.6 or user flags → forward to admin with query + top context
   * Admin correction stored → new doc chunk or canonical answer inserted & embedded → upsert

**Experiment ideas (research):**

* Compare precision@k and hallucination rate for:

  * LLM-only vs RAG w/ embeddings
  * RAG w/ vector-only vs RAG + KG linking (entity grounding)
* Active learning: measure reduction in unanswered queries over time after admin corrections

# 11 — Metrics & Targets (What to measure)

**Product metrics**

* Daily active users (DAU) — target 50–200 in pilot
* Query volume/day — target 200+ in pilot
* Resolution rate (first-response accepted) — target ≥ 80% after 2 weeks of corrections
* Avg response latency — target < 3s (cached), < 6s (cold)

**ML metrics**

* Precision@k for retrieval (k=5) — target ≥ 0.7
* Hallucination rate (human-labeled) — target < 10% after RAG+KG
* Correction frequency — % queries needing admin → target < 20% after 2 weeks
* Improvement in accuracy post-corrections — show % increase

**Research metrics**

* Compare hallucination & precision across methods (LLM-only vs RAG vs RAG+KG) — show stat table & graphs
* A/B testing: show user satisfaction change with admin corrections

# 12 — Privacy & Ethics

* Do not index PII unless you have consent (phone numbers, personal emails)
* Rate-limit public access to avoid scraping abuse
* Provide “report incorrect” and “request deletion” options
* Store logs for minimal time (30 days recommended) unless required for audit
* Use hashed user IDs for analytics; no raw personal data in analytics tables
